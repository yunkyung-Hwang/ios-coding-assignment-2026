# ADR-0004: 상태 관리

상태: 채택

## 맥락
- 요구사항이 목록·상세의 찜 상태 동기화 명시 (R-05)
- 상태 관리 구조는 자유

## 결정
- `@MainActor @Observable` 객체 + MVVM
- 찜은 `FavoriteStore` 단일 인스턴스를 두 화면이 공유
- `FavoriteStore` 를 프로토콜로 `FavoriteKitInterface` 에 두고 구현은 `FavoriteKit`
- 찜 여부를 상품 엔티티에 넣지 않음
- 찜 전용 UseCase 타입을 두지 않음. `FavoriteStore` 가 유스케이스 경계

## 근거
- Observation 은 iOS 17 표준. 외부 의존 없이 프로퍼티 단위 무효화 제공
- 공유 지점을 하나로 두면 동기화가 코드가 아니라 구조로 보장됨.
  화면별 로컬 상태는 갱신 누락 시 불일치가 발생
- 찜과 상품을 분리 보관하면
  - 목록 재조회 시 찜 유지
  - 찜 변경 시 목록 재조회 불필요
  - 원격·로컬 데이터가 화면에서만 결합 (요구사항의 책임 구분)
- 소비자가 "변경을 알린다" 를 알아야 언제 다시 읽을지 판단 가능.
  프로토콜에 `Observable` 을 상속시켜 그 의도를 표기.
  다만 이는 "구현체가 `@Observable` 이다" 까지만 보장하고
  개별 프로퍼티의 추적 여부는 강제하지 못함. 그 부분은 테스트로 고정
- 찜의 규칙은 토글 하나. UseCase 타입을 두면 Repository 를 그대로 위임하는 계층만 늘어남.
  상태 소유·낙관적 갱신·롤백을 책임지는 `FavoriteStore` 가 실질적 경계

## 기각한 대안
- **AsyncStream 팬아웃** — 다중 구독 시 이벤트가 소비자 간 분배되어 화면별 상태가 어긋남.
  소비자 둘로 실행해 확인함
- **화면별 로컬 찜 상태** — R-05 를 코드 규율로만 보장. 갱신 누락이 곧 버그
- **상품 엔티티에 isFavorite 보유** — 원격 응답에 없는 값을 엔티티가 가짐.
  목록 재조회마다 병합 코드 필요
- **Store 를 구현 모듈에 배치** — `ProductFeature` 가 `FavoriteKit` 구현에 의존하게 되어 DIP 붕괴
- **Interface 에 구체 클래스 배치** — 계약 모듈에 구현이 유입. "Interface 는 계약만" 규칙에 예외 발생
- **TCA** — 외부 의존. 과제 규모에서 Observation 만으로 충족

## 트레이드오프
- `FavoriteKitInterface` 가 Observation 에 결합. 관찰 의도를 타입으로 표기한 대가
- 프로토콜 경유라 `@Environment`·`@Bindable` 사용 불가. 생성자 주입만 허용
