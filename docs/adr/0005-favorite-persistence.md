# ADR-0005: 찜 영속화

상태: 채택

## 맥락
- 앱 재실행 후에도 찜 유지 필요 (R-04)
- 로컬 저장 방식은 자유

## 결정
- JSON 파일 + `actor` (`StorageKit.FileStore`)
- `FavoriteRepository` 프로토콜 뒤에 배치
- 읽기는 메모리 상태, 쓰기만 파일
- 저장 실패 시 해당 항목만 이전 값으로 복원
- 적재 실패는 파일 손상으로 간주. 빈 목록으로 시작하고 다음 저장이 파일을 대체

## 근거
- 저장 대상이 ID 집합 하나. 관계 질의·부분 갱신·스키마 마이그레이션 없음
- `actor` 로 파일 접근 직렬화 + 원자적 쓰기 → 동시 저장·중단 시 파일 손상 방지
- 셀 렌더링마다 저장소를 조회하지 않음. 찜 판정은 메모리 집합 조회
- 전체 스냅샷이 아니라 토글한 항목만 되돌림 →
  동시 토글 중 한 건이 실패해도 다른 항목의 변경이 유실되지 않음
- 저장 방식 교체 시 `FileFavoriteRepository` 만 대체
- 두 실패의 취급이 다른 이유
  - 적재 실패는 "파일은 있으나 읽지 못함" 뿐. 첫 실행은 파일 부재라 실패가 아님
  - 사용자가 취할 조치가 없고 재시도해도 결과가 같음. 다음 저장이 자동 복구
  - 저장 실패는 토글이 되돌아가는 것으로 화면에 드러남. 별도 문구는 요구사항 밖

## 기각한 대안
- **SwiftData** — ID 집합 저장에 컨테이너·모델 정의가 과함.
  `@Model` 이 참조 타입이라 `Sendable` 도메인 타입과 섞으려면 매퍼가 추가로 필요
- **CoreData** — 같은 이유에 보일러플레이트가 더 큼
- **UserDefaults** — 설정 저장소를 사용자 데이터 저장소로 전용. 용량·동시성 보장 없음
- **Keychain** — 민감 정보가 아니므로 암호화 비용만 발생
- **토글마다 전체 재조회** — 파일 I/O 가 화면 갱신 경로에 들어감

## 트레이드오프
- 항목 증가 시 저장마다 전체 직렬화. ID 집합 규모에서는 무시 가능
- 손상 파일은 복구하지 않고 대체. 이전 찜 목록은 되살리지 못함
